> **只给自己用的两个页面** — 一页「识别」：把一箱退货照片拖进去，逐行核对后导出 CSV 贴回 Excel；一页「对账」：把应到表拖进去，跟这次的识别结果逐件比，直接出缺货清单。

## 项目背景

自从有了 AI，把很多以前做不了的想法慢慢做出来了 — 这个是其中最"土"的一个：仓库退回来的货，箱子拆开一摞照片，人工一个个抄运单号、抄贴纸上的编号和日期，抄完贴进 Excel 交给下游。活本身不难，但量大、重复、还不能抄错。

以前只能硬抄，现在能拍下来直接读。整个工具就为了这一件事：**把照片变成能贴进 Excel 的三列**。

## 我做了什么

两个版本，同一套接口：

- **macOS 原生版**：Swift 写的 CLI + 一个最小 HTTP 服务，识别全靠系统自带的 Vision 框架（`VNDetectBarcodesRequest` / `VNRecognizeTextRequest`）——零第三方依赖，不用装 zbar、OpenCV、Python。`build.sh` 编出一个二进制扔哪都能跑。
- **Linux 容器版**：Vision 是 macOS 专有的，服务器上跑要换识别件。等价替换是 zxing-cpp 解码 + RapidOCR（PP-OCR）认字 + Pillow 处理图像。HTTP 层两边完全一致，`POST /api/recognize` 的请求响应格式一模一样，前端一行都不用改。

### 识别策略：三层

运单号和 LYRD 编号走了三层，从可靠到兜底：

1. **条码解码** — 最可靠。运单号和贴纸编号各有一根条码，两个号都能直接解出来。
2. **整图 OCR** — 条码糊了时的兜底。同一行的碎片要拼回一行，否则号码会被读成两段断开的字符。
3. **多角度兜底** — 定位运单号所在的那一行，旋转若干档 + 对比度增强后再读一遍，面单斜拍时效果显著。**这一层的结果只是候选，界面上标出来让人核对。**

日期单独处理，因为贴纸上印的年月日有三种形态：

- 严格「年月日」形态 → 整图可信，直接取
- 连字符形态（`2026-08-19`）→ 只在**贴纸区域内**认，全图认会命中网页截图里的时间戳
- 纯数字流 → 也是只在贴纸区域内认

贴纸区域怎么找？用 LYRD 条码的 bbox 往上扩三倍（日期在条码上方）。但它是**定位器不是硬过滤** —— 有几张贴纸是横躺的，日期落在贴纸框外，所以还得有整图兜底。

### 踩过的三个坑

- **EXIF 方向必须处理**。手机竖拍的照片不套用 `kCGImagePropertyOrientation` 的话，条码方向是错的，整张图都解不出来。
- **不能只靠 OCR 读号**。OCR 会把一串运单号读成两段或读错位，条码解码才是唯一可靠来源。
- **日期宁可留空也不猜错**。拼错一个日期比没有日期更麻烦 —— 认不出来就空着。

### 识别不准的边界在哪

OCR 会把 `0` 读成 `o`、`b` 读成 `l`。对账环节碰到疑似匹配时**只给提示，不自动算成「已到」** —— 宁可让人多看一眼，也不能让「自动认了」把真缺货盖掉。

同样地，几个承运商的号码格式不一样（有的 11 位纯数字，有的字母数字混排），脚本**不按承运商区分规则**，一律「条码优先 + 通用正则兜底」，避免写死一套规则后换个承运商就全错。

### 对账页：先给结论，再摆数

拖进一张应到表（xlsx）+ 这次的识别结果（CSV，或直接用本次拍的照片），逐件比，出缺货清单。

口径是刻意设计过的：

- **逐件**。同一唛头可以有多件，`应到 = 已到 + 缺` 恒成立。
- **应到件数按表里的「数量」列算，不是按行数**。同一唛头写 2 件就算 2 件，跟表尾的合计件数对得上。
- **表里只写了前缀的唛头照样算进应到**，不会悄悄少算。
- **表里没有的唛头算「表外」，表里有但照片多的算「多认了」**，都不混进「已到」。

还有一条我觉得比功能更重要：**还没拿到到货结果时，不说「缺多少」**，只说表读到了多少件、多少种唛头。账还没开始比就说「缺 28 件」，那是吓唬人。

### 识别引擎的几轮反复

- 最初接了个额外的 OCR HTTP 服务想并行提速，结果它**线上卡死过 4 次** —— 那个服务是单线程的，卡了只能 `docker restart` 拉起来，换来的收益是快约 15%、准确率零优势。后来整个删干净了（容器、镜像、watchdog、代码里的客户端），根因消失才算完。
- 换过一次新版 OCR 包，新旧两版的检测/识别超参一字不差，所以回归 diff 出来的每一行变化都能干净归因到「模型本身变了」。
- 模型档位在页面上可切，四档全烤进镜像，**运行时切换不联网**。默认档位是反复实测后定的：有一档更快的版本在 4 张小字长号上把 `0` 认成字母、把整段认错，比速度更要紧。

### 性能

OCR 线程数是实测出来的曲线，不是猜的：

```
1→2.81s  2→1.74s  4→1.29s  6→1.12s  8→1.06s  12→1.23s  16→1.88s
```

8 线程最快，再往上反而慢（线程同步开销比省下的算力还多）。前端上传并发从 3 路降到 2 路 —— 3 路以上纯属多占核不干活，同进程里多线程抢同一个线程池，4 路吞吐反而掉。单张识别 2.23s → 1.89s。

## 已知未解 / 显式没做

- ❌ **macOS 版的正则改动没有在完整样本上验证过** —— 样本照片按要求全程留在服务器，照片没落地 Mac。这是最大的盲区，只能靠逐条对齐的正则单测兜。
- ❌ **macOS 版还没重新发版** —— 代码改了、编译通过，但日常用的还是旧二进制。
- ❌ **唛头号那一行印在方框里、检测分数低**，默认阈值检不出来，目前靠降阈值重扫兜，还没有更稳的做法。
- ❌ **到货单上的长号码**用旋转变换的思路在试，参数还在对拍，没定版。

## 验证方式

40 张真实照片（退货 20 + 到货 20）做回归基线，每改一版识别逻辑就跑一遍，逐行 diff：

- 换引擎、换模型、调阈值之后，**基线里每一行的变化都能指出是哪张图、哪个字段变了**
- 改完必须跑回归、必须跟基线逐行比，不靠"看着挺准"

前端逻辑（对账口径那些）另外有断言式自测，几十项断言覆盖每条规则。
