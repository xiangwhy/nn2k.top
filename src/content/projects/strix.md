> **agent 给线索，人工给证据** — 三次扫描里，agent 报出的每一条都要我用 curl 重放一遍才算数；反过来，agent 没归档的那条 Critical，是从它 18 MB 的中间数据库里捞出来的。

## 项目背景

自从有了 AI，把很多以前做不了的想法慢慢做出来了 — 这条最直接。以前请人做一次渗透测试要排队等档期，现在自己机器上跑一条命令就能出一份报告。但真正用下来的结论跟预期相反：**报告本身不是交付物，报告引发的怀疑才是。**

所以这个项目其实不是「装了个工具」，是「搞明白怎么用这个工具，以及它什么时候会骗我」。三次扫描，三个 strix 版本，三个完全不同的局面，正好凑齐了一整套方法论。

被测的两个系统都是自己的：一个 Next.js + Payload 的自建电商站，一个自用的 ERP。授权是明确的，报告细节全部脱敏 —— 本文只留方法和判断，具体的漏洞细节、真实标识符、完整 PoC 都不公开。

## 我做了什么

三次扫描，用的都是 [strix](https://github.com/usestrix/strix)（开源 AI 渗透 agent，Docker 沙箱 + 多个子 agent 分工：侦察 / 漏洞利用 / 后渗透 / 报告）。它自己会开 Kali 沙箱容器、挂 Caido 代理抓包、带 Playwright 和一堆现成工具（nmap、nuclei、sqlmap、ffuf）。

### 第一次：agent 说有，人工说好（strix 1.1.0）

扫自建的 Next.js 16 + Payload CMS 电商站（内网 dev 实例）。deep 模式跑下来报了 **8 条高/中危**，整体评级 High → Critical。

问题集中在两处：

- **应用跑在 `next dev` 上**，而这个实例对外可达。每个 500 错误页都把完整堆栈、绝对路径、OS 用户名和全部依赖的精确版本吐出来 —— 攻击者拿到就能直接做针对性 CVE 选择。
- **中间件只有 i18n 一条**，用负向 deny-list 把 `/admin/` 和 `/api/` 排除在 locale 重写之外。等于没有边缘层的 auth gate，Payload 的 admin UI 和 REST API 都能匿名直达。

组合起来是三条绕过路径：locale 前缀（`/en/admin`）、前端路径遍历（`/products/../admin`）、URL 规范化绕过（`/api/..`），任意组合都能到达 Payload 处理函数。

这次踩到的坑比漏洞本身更值钱：

- **目标中途崩了** —— 扫描后期实例返回 "No route to host"，strix 自己结束后也没法复测。那几条依赖「业务影响」结论的发现，只能靠结构化证据（ETag、响应体哈希、`x-middleware-rewrite` 头）撑着，完整 exploit 链路没跑通。
- **模型选错了** —— 用的不是官方推荐的编码模型，LiteLLM 的成本估算对这个模型失效。报告里只能明写「事实层以直接观察的 HTTP 证据为准，业务影响判断为保守解读」。
- **证据强度不一** —— 8 条里只有一部分我独立 curl 复现过，剩下的靠 SARIF 输出。

结论：**strix 1.1.0 是个线索生成器，不是结论生成器。**

### 第二次：复测比首扫更值钱（strix 1.4.1）

三周后拿 1.4.1 复测同一边界。跑之前先做了一件事：**把上次的 8 条做成对照表**，每条标注「独立验证 / 仍存在 / 部分修复」。

结果很难看：**8 条一条没修**。

| 上次的结论 | 这次 | 关键新证据 |
|---|---|---|
| dev 模式堆栈泄漏 | ❌ 仍存在 | `/admin` 从 500 变 200，但 body 里仍嵌着 `node_modules/.pnpm/...` 路径 |
| dev middleware manifest 暴露 | ❌ 仍存在 | 200，返回完整 matcher 正则 |
| dev 构建产物公开 | ⚠️ 修了一半 | `react-refresh.js` 已 404，dev manifest 仍可达 |
| locale 前缀绕过 | ❌ 仍存在 | `/en/admin`、`/zh/admin` 都 200 |
| 路径遍历 | ❌ 仍存在 | MD5 等价：`/api/products` ≡ `/products/../api/products` ≡ `/api/%2e/products` |
| `/contact` 泄漏运营者 PII | ❌ 仍存在 | 邮箱、手机号、WhatsApp、社交账号全部公开 |
| admin / api 无认证墙 | ❌ 仍存在 | `/admin` 200 匿名可达，`/api/users/me` 返回 null 用户 |
| `/api/..` 规范化绕过 | ❌ 仍存在 | `/api/%2e%2e/admin` 200 |

中间升过版本（Next 15 → 16，Payload 3.86 → 3.87），**版本升级没有解决任何一个问题** —— 因为根因不在依赖，在「应用跑在 dev 模式」和「中间件写成了 deny-list」这两个决定上。

strix 1.4.1 这次另外补了 8 条新发现（Turbopack HMR 的 WebSocket 路由表泄漏、`/api/access` 把 access rules 拓扑整个吐出来、`/admin/api/*` 大小写不敏感路由、launch-editor 存在性 oracle、`/api/globals/contact` 结构化 PII、`/api/articles` 全文公开等）。

**这次最有用的一招是 MD5 等价校验**：不比内容、不比状态码，直接比响应体的 MD5。「`/api/products` 和 `/products/../api/products` 的 MD5 一样」这一句话就把「路径遍历存在」从推测钉成了事实，而且不需要任何权限、不触发任何写操作。

### 第三次：agent 挂了，线索还在（strix 1.7.0）

换了自用的 ERP 系统，strix 升到 1.7.0，deep 模式、非交互式，跑 46 分钟。

这次的局面完全不同 —— **扫描没跑完**：

```
status: stopped    exit_reason: rate_limited    complete: false
```

配额耗尽，25 个 agent 挂了 21 个，Root Agent 被迫停止。统计下来：覆盖攻击面 98 项，outcomes 是 reported 2 / no_issue_found 13 / ruled_out 40 / needs_follow_up 39，**gaps 54 个**，最终归档的 finding 只有 1 条（Medium）。

**但那条 Critical 就是这么丢的。**

strix 内部的 agent 在被 429 打断之前，已经确认并写进共享 note 了 —— 一个未认证的接管链：注册端点在店铺 ID 上幂等，对已入驻店铺重复注册会返回**既有且已批准**的代理 ID，攻击者自选的设备密钥随即成为该代理的有效凭据；随后可以冒充该代理读取命令队列，并向**真实在用店铺的订单管道写入伪造订单**，污染分单、审核和回款金额。

整个过程**每一步都未认证**。而且这条发现不依赖任何秘密：供应商自己公开发布的扩展包里就带着真实店铺的 ID 和店名配对 —— 一个公开可知的字符串被当成了授权因子。

问题在于 Root Agent 中断，这条没能归档成正式 finding。它躺在一份 18 MB 的 SQLite 中间产物里 —— 6299 条消息、236 条接管 agent 消息。

**我从那个库里把证据链还原了出来**：注册请求 → 幂等返回既有代理 → 用自选密钥读 `/status`（200，`agentStatus: active`，且同步时间戳早于我第一次探测 11 分钟，证明是活的生产代理）→ 读命令队列 → 注入一条合成订单（201）→ 跨店写入对照（403，被正确拒绝）。

还有一条反证值得写：**旧密钥是累加不是轮换**。在受害代理上连续注册 3 次，3 个密钥**全部**返回 200。也就是说店主的密钥没被作废（没有同步 DoS），但攻击者永久持有并行凭据 —— 修复时仅覆盖写入无效，必须显式吊销历史密钥。

## 沉淀下来的四条

### 一、agent 报的是线索，人工复核出的是证据

三次都一样。agent 报的每一条，我都要用 curl / python 重放一遍才算数。判定标准很硬：**只有能重放、能比对、能留证（状态码 + 响应体哈希 + 完整报文）的才算发现。**

复现时优先用**无副作用**的探针：比 MD5、比 ETag、比响应体大小，而不是真的去写一条脏数据。顺序反过来——先想清楚怎么不破坏现场再动手。

### 二、结论必须分层：事实、推断、猜测

agent 的输出经常把三层混在一起。我把它拆开写：

- **事实** —— 「返回 200，body 含绝对路径」。直接观察，不需要相信谁。
- **推断** —— 「这条路径能绕过认证墙」。由事实推出，但依赖我对代码意图的假设。
- **猜测** —— 「若再存在 nginx alias off-by-slash 缺陷，则可读取根 CA 私钥，严重性应大幅上调」。

猜想要单独标出来，因为它最容易被当成结论转述出去。

### 三、证伪比找漏洞更重要

上面那条猜测就是例子。strix 报告认为严重性应该上调，理由是如果路径穿越成立就能读到 CA 私钥、进而对全部操作员会话做 TLS 中间人。

我实测了 8 种穿越变体（`--path-as-is` 绕过 nginx 归一化、URL 编码、缺分隔符、混合形式），**全部**被 nginx 归一化后回落成 SPA 的 `index.html`（响应体一律 517 B 的 `<!doctype html>`）。路径不可达。

结论：**维持 medium，不升级。**

一个 agent 的「如果……就能……」如果不验证就往下传，会变成一个错误的危告警 —— 而错误的危告警比漏报更消耗信任。宁可花一轮把漏洞打掉。

### 四、复测要把账算清

第二次扫描的产出是那张对照表：每条旧发现标「仍存在 / 部分修复 / 已修复」，每条给出新证据。八条一条没修这个结论本身，比任何单条漏洞都更有价值 —— 它指出的不是「有洞」，而是**修法是错的**。

用户其实清理过 dev 构建产物（`react-refresh.js`、`main-app.js` 都已经 404），但根因还在：**删文件是打地鼠，切换运行模式才是修根因。** 报告里把这条写在了最前面。

## 报告怎么收尾

安全报告的最后一页比第一页重要。11-03 那次我给的是按优先级排的处置清单：

1. **清理注入的测试数据** —— 那条伪造订单和批量赋值批次都真实躺在店铺订单表里，会进入分单和回款流程。
2. **吊销全部历史设备密钥** —— 因为是累加语义，覆盖写入无效。
3. **审计代理列表** —— 这次评估创建了数百个 pending 代理和店铺行，得批量清理，同时核查有没有非评估方的未授权注册。
4. **把另一个公网实例纳入资产清单** —— 它跑着同一套 API、同一版本，证书体系却不同，strix 把它标成 out-of-scope 没深测，我是手工比对健康检查指纹才发现的。

还有一条**当时就判定不需要做的**：strix 提示扩展包里可能夹带 CA 私钥。我对解包后的全部文件递归 grep 私钥头，零命中 —— 包里只有公钥证书。这条不升级严重性。

## 验证方式

- **复现**：所有结论都用 `curl` / `python3 urllib` 独立重放过一遍，不引用 strix 的 SARIF 作为唯一证据。
- **等价性**：涉及「绕过」类结论用响应体 MD5 等价证明，不靠肉眼比对。
- **交叉验证**：Caido 代理的 exchange id 可以回溯原始报文（注册 → 接管 → 读状态 → 注入 → 跨店对照每一跳都有 id）。
- **回归**：修完一条复扫一条，不能一次性全修再统一验证 —— 中间出问题分不清是修坏的还是本来就坏的。
- **断言**：报告里每条修复建议都写清「怎么算修好了」，可直接当验收用例。

## 已知未解 / 显式没做

- ❌ **11-03 那次有 39 项 `needs_follow_up` 没复扫** —— 权限提升、IDOR、付款审批工作流滥用、批量赋值提权、XLSX 上传 XXE / zip bomb、审计日志越权范围、会话管理细节，全都要登录态才能测。配额耗尽时这些都断了。
- ❌ **四个独立验证 agent 因 429 没跑完** —— 包括角色越权、跨域绕过、凭据注入、扩展桥接四个方向的验证。
- ❌ **Critical 链的独立复现没补跑** —— 审批服务当时超时，取证链是 strix 侧实测 + Caido 报文 + 代理历史 provenance 三方拼出来的，不是我从头手搓的。
- ❌ **没接 CI** —— strix 支持 GitHub Actions 里做 PR 级门禁，但我这边目标都是自建服务，跑一次全量扫描当定期体检更合适。
